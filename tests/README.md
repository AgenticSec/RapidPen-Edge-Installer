# Edge Installer のテスト

インストーラを実際のコンテナ上で動かし、**利用者の端末から見た振る舞い**を検証する。

## 実行方法

```bash
./tests/run.sh                        # 全ケース（既定は ubuntu:22.04）
./tests/run.sh --base ubuntu:26.04    # ベースイメージを指定
./tests/run.sh with-env               # ケースを指定（複数可）
./tests/lint.sh                       # 構文チェックと静的解析
```

必要なもの: `docker` / `expect` / ネットワーク（インストーラが GitHub Release を参照するため）。

## ケース一覧

| ケース | 条件 | 期待する振る舞い |
|---|---|---|
| `with-env` | 端末あり・設定あり | 入力を求めずに進み、設定が保存される |
| `with-env-no-tty` | 端末なし・設定あり | 同上（構成管理ツールからの実行） |
| `missing-api-key` | 端末あり・設定なし | **入力待ちに落ちず**、案内を出して直ちに終了する |
| `no-tty` | 端末なし・設定なし | 同上 |

## なぜ端末を用意してテストするのか

このインストーラは**対話入力を行わない**が、利用者は端末のある環境で実行する。
過去に「端末があると入力待ちで永久に止まる」不具合があったため、端末を与えた状態で
**ハングしないこと**を確認する必要がある。`expect` で実端末（pty）を作るのはこのため。

### 背景となった不具合

かつてインストーラは API キーを端末から読んでいた。この方式は `sudo` の擬似端末
（pty）実装に依存する。`sudo` が `use_pty` で作った pty のフォアグラウンド
プロセスグループを子プロセスに設定しない場合（Ubuntu 26.04 で確認）、インストーラは
バックグラウンドプロセスグループのまま端末を読むことになり **SIGTTIN で停止**する。

このとき利用者に見えるのは次の状態で、原因にたどり着く手がかりが無い。

- プロンプトは表示される（端末への**書き込み**は許される）
- 打鍵した文字も画面に出る（端末ドライバの**エコー**であって、プロセスとは無関係）
- Enter を押しても何も起きない（プロセスは既に**停止**している）

同じ構成でも Ubuntu 22.04 / 24.04 では再現しない。`sudo` の版差に左右されるため、
インストーラ側では対処しきれない。そこで**端末に触れること自体をやめ**、設定は
環境変数で受け取る方式に変えた。Web UI が API キーを埋め込んだインストーラを
配布するので、利用者が手で入力する場面は無い。

## 仕組み

インストーラは本番では次の形で実行される。

```bash
curl -fsSL .../install.sh | sudo sh
```

この形では `sudo` の標準入力がパイプになり、そこから呼ばれる `setup.sh` も EOF 済みの
パイプを標準入力として受け取る。テストでも同じ形を保っている（`tests/bootstrap.sh` が
`install.sh` の役割を担い、GitHub からアーカイブを取得する部分だけを作業ツリーの内容に
差し替えている）。

コンテナ内の構成は以下のとおり。

- **`docker`（`docker-stub.sh`）**: イメージ取得は行わない。20GB 近い Operator イメージを
  CI で引くのは現実的でなく、取得の成否はインストーラのロジックとは独立しているため
- **`systemctl`（`systemctl-stub.sh`）**: `start agenticsec-supervisor` だけを失敗させ、
  そこでインストーラを終わらせる。コンテナに systemd が無いことに加えて、
  失敗時クリーンアップ（`cleanup_on_error`）が `/etc/agenticsec` を丸ごと消してしまい、
  生成された `state.json` を検査できなくなるのを避ける狙いがある
- **`setpriv` による降格**: `su` / `runuser` は新しいセッションを作って制御端末を落として
  しまうため使えない。実端末を保ったまま一般ユーザーになるために `setpriv` を使う
- **`Defaults use_pty`**: Ubuntu / Debian の既定に近づけてある

## XFAIL（既知の失敗）

`run.sh` の `XFAIL_CASES` に載せたケースは、失敗しても全体の結果を赤にせず `XFAIL` として
報告する。まだ直っていない不具合をテストとして先に書けるようにするための仕組み。

- 不具合を直す PR では、`XFAIL_CASES` から該当ケースを外して `PASS` になることを示す
- `XFAIL_CASES` に載っているケースが通った場合は `XPASS` として報告される。
  直ったのにリストに残っている状態なので、リストから外すこと

## ケースを追加するには

1. `tests/case.sh` にコンテナ内の条件を足す
2. 端末が要るなら `tests/drive.exp` に、要らないなら `tests/run.sh` に判定を足す
3. `tests/run.sh` の `ALL_CASES` に名前を足す
4. 現行コードで失敗するケースなら `XFAIL_CASES` にも足す
